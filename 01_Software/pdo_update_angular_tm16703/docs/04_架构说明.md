# 04 架构说明

## 1. 架构原则

当前工程围绕以下原则组织：

- 单一职责
- 单向依赖
- 单一状态所有权
- 控制与执行解耦
- 上传只反映真实状态
- 错误按域隔离，不整帧连坐

## 4. 关键架构路径

### 4.1 下行路径

```text
USART1 IRQ / DMA
-> bsp_uart_driver
-> uart_rtos
-> uart_stack
-> host_protocol parser
-> uart_task_apply_command
-> host_control_cmd(mailbox)
-> control_task_apply_slave_motion
-> robot_motion_cmd
-> Motor_Task
-> motor_cmd_* / bsp_motor_handler
```

### 4.2 上行路径

```text
motor info / battery / ibus / gpio / can diag
-> drive_feedback_service / telemetry_service
-> uart_task_build_telemetry_tlv
-> host_protocol builder
-> uart_stack
-> bsp_uart_driver TX
```

### 4.3 回零路径

```text
control_task_joint_home_request_update_10ms
-> motor_task_joint_home_request_set
-> Motor_Task
-> motor_task_process_joint_home
-> 关节使能/寻底/清零/置零
```

## 5. 任务与职责分工

### 5.1 `ContronlTask`

职责：

- 每 10ms 执行当前模式
- 每 50ms 采样遥控模式输入
- 在 `SUB_SLAVE` 下把 host mailbox 转换成 `robot_motion_cmd`
- 在手动模式下把 IBUS 输入转换成 `robot_motion_cmd`

边界：

- 不直接下发电机使能、失能、复位
- 不拥有 host mailbox

### 5.2 `Motor_Task`

职责：

- 电机使能/失能仲裁
- reset 边沿执行
- 关节回零状态机
- 底盘速度与关节位置下发

边界：

- 不解释遥控模式来源
- 不直接解析 UART 协议

### 5.3 `Robot_Speed_Task`

职责：

- 从电机反馈采样真实轮速
- 刷新 `drive_feedback_t`

### 5.4 `uart_task`

职责：

- 启动 UART1 协议服务
- 维护会话活性和命令新鲜度
- 解析命令 TLV
- 维护 power-policy 锁存语义
- 周期构建遥测帧

边界：

- 不直接控制电机
- 不拥有模式机
- 不回显 host 意图冒充真实遥测

### 5.5 `telemetry_service`

职责：

- 聚合真实轮速、升降位置、电池、IBUS、急停、CAN 诊断
- 生成 `status_word / health_word / alarm_info`
- 决定可选字段是否可上报

边界：

- 不拥有 UART1 协议状态
- 不写 host mailbox

## 6. 并发与一致性策略

### 6.1 临界区

当前通过临界区或 IRQ guard 保护以下共享状态：

- host mailbox
- mode 状态
- motion command
- drive feedback
- joint home 状态机
- UART 会话时间戳与锁存状态字

### 6.2 为什么不使用队列承载全部控制数据

当前选择共享快照而不是每次命令都入队，原因是：

- 需要保留“最近一次有效命令”语义
- 执行层更适合按固定周期读取稳定快照
- 可直接实现会话超时、命令新鲜度和 post-entry epoch 判定

代价：

- 必须严格定义所有权和临界区边界
- 必须避免出现双真值

## 7. 安全设计

### 7.1 通信安全

- 会话超时 `1s`
- drive 命令新鲜度 `1s`
- lift 命令新鲜度 `1s`
- 越界值拒绝
- drive 必须双轮同帧
- 解析按域隔离

### 7.2 执行安全

- 急停优先级最高
- host disable 可阻断指定电机
- 关节回零前禁止绝对位置控制
- 回零故障进入 fault 状态

### 7.3 上传安全

- 上传仅反映真实状态
- 未接入传感器的字段不伪造有效值

## 8. 当前架构中的明确取舍

### 8.1 READY 模式功率语义

当前执行层默认将 `MODE_READY` 视为无力矩安全态，不允许驱动轮保持上电。若项目确需“带电待命”，只能通过 `SYSTEM_CFG_READY_KEEP_DRIVE_POWER=1` 显式开启。

### 8.2 历史协议兼容

当前代码不再保留 `v_linear / w_angular` 的历史别名，也不再发送 ACK。后续联调必须以当前接口文档为准。

### 8.3 可选遥测字段

`bucket_volume` 被定义为可选字段，只有真实数据源接入后才允许发送。

## 9. 后续扩展建议

如果继续向工业化靠近，下一阶段建议按以下顺序推进：

1. 为 `READY` 带电待命增加板级安全联调用例，仅在确有需求时再启用
2. 为 spray / drain / gripper 接入真实执行器状态源
3. 为 `bucket_volume` 接入真实传感器源
4. 增加系统级故障码和统一事件日志
5. 增加板级回归测试与协议一致性测试
