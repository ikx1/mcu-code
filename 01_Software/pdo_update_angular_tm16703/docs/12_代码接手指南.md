# 代码接手指南

## 1. 这份文档解决什么问题

这不是一份“介绍项目是什么”的文档，而是一份“下一个人第一天接手时该怎么看、该从哪里下手、改一处会影响哪里”的实战指南。

如果你只打算花 1 小时熟悉项目，优先看这份文档，然后再看：

1. `docs/02_软件架构设计文档.md`
2. `docs/03_模块设计文档.md`
3. `docs/04_接口文档.md`

## 2. 先建立一个正确的心智模型

这个工程的核心不是“串口收发”本身，而是以下 5 层单向链路：

```text
UART1 字节流
-> 协议帧
-> host mailbox
-> 控制层运动命令
-> 执行层电机动作
-> 真实反馈再上报
```

也就是说：

- 串口层不直接控电机
- 控制层不直接发 CAN
- 遥测层不回显主机意图
- 共享状态都必须有唯一写入口

接手这个项目时，只要你守住这 4 条，后续改动就不容易把系统搞乱。

## 3. 第一天建议阅读顺序

### 3.1 第 0 步：先看目录，不要直接钻函数细节

推荐先扫一遍这些目录：

- `Core/`
- `User/`
- `BSP_Plantform/`
- `MCU_Platform/`
- `Middlewares/components/`
- `docs/`

理解它们的角色：

- `Core/` 是 CubeMX 和板级初始化入口
- `User/` 是真正的业务逻辑
- `BSP_Plantform/` 是板级设备与集成适配
- `MCU_Platform/` 是 STM32F4 相关移植层
- `Middlewares/components/` 是可复用中间件

### 3.2 第 1 步：从启动路径看任务怎么起来

推荐阅读顺序：

1. `Core/Src/main.c`
2. `Core/Src/freertos.c`
3. `User/User_Init/User_Init.c`

重点函数：

| 文件 | 函数 | 位置 | 你需要知道什么 |
| --- | --- | --- | --- |
| `main.c` | `main()` | 工程入口 | 初始化哪些外设、哪些外设其实没启用 |
| `freertos.c` | `MX_FREERTOS_Init()` | `:73` | RTOS 初始化后从哪里进入用户任务 |
| `User_Init.c` | `UserAppTask_Init()` | `:129` | 先拉起哪些服务，再创建哪些任务 |
| `User_Init.c` | `user_app_task_entry()` | `:85` | 实际任务优先级、栈大小、启动顺序 |

你看完这 4 个函数后，应该能回答两个问题：

- 系统上电后有哪些任务一定会运行？
- UART1 新协议服务是在调度器启动前还是启动后完成注册的？

### 3.3 第 2 步：顺着 UART1 主链看一条命令怎么进系统

推荐阅读顺序：

1. `Core/Src/stm32f4xx_it.c`
2. `MCU_Platform/MCU_Core_UART/uart_irq_adapter.c`
3. `MCU_Platform/MCU_Core_UART/uart_port.c`
4. `BSP_Plantform/Bsp_Drivers/communication/driver/bsp_uart_driver.c`
5. `BSP_Plantform/Bsp_Integration/uart/uart_rtos.c`
6. `BSP_Plantform/Bsp_Integration/uart/uart_stack.c`
7. `Middlewares/components/host_protocol/host_protocol.c`
8. `User/communication_task/uart_task.c`

关键函数位置：

| 函数 | 文件:行 | 作用 |
| --- | --- | --- |
| `USART1_IRQHandler()` | `stm32f4xx_it.c:230` | UART1 中断入口 |
| `DMA2_Stream2_IRQHandler()` | `stm32f4xx_it.c:323` | UART1 DMA RX IRQ |
| `DMA2_Stream7_IRQHandler()` | `stm32f4xx_it.c:349` | UART1 DMA TX IRQ |
| `mcu_uart1_usart_irq_adapter()` | `uart_irq_adapter.c:6` | IDLE 中断转驱动事件 |
| `uart_port_dma_rx_start()` | `uart_port.c:36` | 启动 USART1 DMA RX |
| `uart_device_init()` | `bsp_uart_driver.c:133` | 建立 FIFO + DMA runtime |
| `uart_rtos_start()` | `uart_rtos.c:71` | 创建 TX/RX 任务 |
| `uart_stack_start()` | `uart_stack.c:104` | 把字节流挂到协议解析 |
| `uart_parser_feed()` | `host_protocol.c:48` | 流式帧解析 |
| `uart_task_apply_command()` | `uart_task.c:381` | 真正把命令写进 mailbox |

### 3.4 第 3 步：看命令如何从 mailbox 变成电机动作

| `robot_mode_update_50ms()` | `control_task.c:495` | 急停/遥控决定当前模式 |
| `control_task_apply_slave_motion()` | `control_task.c:625` | host 命令转左右轮 rpm 与关节目标 |

## 4. 项目里最关键的 6 个状态对象

| 状态对象 | 定义位置 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| `host_control_cmd_t` | `host_control_cmd.h` | `uart_task.c` | `control_task.c`、`motor_task.c` |
| `ROBOT_MODE_T` | `robot_mode_service.h` | `control_task.c` | 显示、执行、灯效 |
| `robot_motion_cmd_t` | `robot_motion_cmd.h` | `control_task.c` | `motor_task.c` |
| 回零状态机 | `motor_task.h` | `motor_task.c` | `control_task.c` 只读 |
| `drive_feedback_t` | `drive_feedback_service.h` | `motor_task.c` | `telemetry_service.c` |
| `telemetry_service_snapshot_t` | `telemetry_service.h` | `telemetry_service.c` | `uart_task.c` |

接手人员必须记住：

- 问题 1：数据到底写到了哪里？
- 问题 2：谁是唯一写者？

很多接手后的 bug，都是因为没先回答这两个问题。

## 5. 最常见的 5 类需求改动，应该怎么下手

### 5.1 改协议字段

从这里开始：

- `host_cmd_defs.h`
- `uart_task.c`
- `host_control_cmd.h`
- `docs/04_接口文档.md`

不要直接从控制层开始改。协议字段没在 `uart_task_apply_command()` 落地前，改控制层没有意义。

### 5.2 改模式逻辑

从这里开始：

- `robot_mode_service.h`
- `control_task.c`
- `ws2812_task.c`
- 必要时看 `motor_task.c`

尤其注意：模式变化不仅影响控制，还会影响电机是否允许上电。

### 5.3 改电机使能/失能策略

从这里开始：

- `motor_task_drive_allow_enable()`
- `motor_task_handle_drive_motor()`
- `motor_task_joint_allow_enable()`

不要把 enable 判定散落到控制层。

### 5.4 改关节回零流程

从这里开始：

- `motor_task_process_joint_home()`
- `bsp_gpio_driver.h`
- `gpio_port.c`

先确认你改的是“状态机逻辑”，还是“限位采样极性”，不要混着改。

### 5.5 改遥测

从这里开始：

- `telemetry_service_snapshot()`
- `uart_task_build_telemetry_tlv()`

如果只是想让上位机“看到命令值”，这是错方向。这里应该只发真实值。

## 6. 现场调试时建议先打的断点

### 6.1 串口不通

- `uart_port_dma_rx_start()`
- `uart_device_init()`
- `uart_parser_feed()`
- `uart_task_on_frame()`

### 6.2 收到命令但不动作

- `uart_task_apply_command()`
- `control_task_apply_slave_motion()`
- `motor_task_apply_drive_motion()`

### 6.3 升降不动作

- `uart_task_apply_command()`
- `motor_task_process_joint_home()`
- `motor_task_apply_joint_motion()`

### 6.4 状态字不对

- `telemetry_service_build_status_word()`
- `telemetry_service_build_health_word()`
- `telemetry_service_snapshot()`

## 7. 第一天最好做的 3 个实验

### 7.1 实验 1：验证协议收包主线

目标：

- 让 `uart_task_apply_command()` 至少命中一次断点

你应该看到：

- `frame->type == 0x81`
- `host_control_cmd_t` 某个字段被更新

### 7.2 实验 2：验证控制到执行主线

目标：

- 让 `control_task_apply_slave_motion()` 和 `motor_task_apply_drive_motion()` 先后命中

你应该看到：

- `robot_motion_cmd_t` 里的左右轮 rpm 非零
- 执行层最终调用 `motor_cmd_set_speed()`

### 7.3 实验 3：验证真实遥测主线

目标：

- 让 `telemetry_service_snapshot()` 被命中

你应该看到：

- 遥测速率与 `UART_TASK_TELEMETRY_PERIOD_MS` 一致
- 上报值来自 `drive_feedback`、电池、IBUS、GPIO 和电机状态

## 8. 接手后最容易误判的事情

### 8.1 “我下发了 enable，所以 status_word 应该立刻显示 enable”

不一定。上传的是执行结果，不是意图。

### 8.2 “我切到 SUB_SLAVE 了，之前那帧命令应该会继续生效”

不会。当前设计要求进入子模式后必须收到新命令。

### 8.3 “READY 模式电机没上电是 bug”

不是。默认配置就是无力矩安全待机。

### 8.4 “lift 命令收到了，关节就应该动”

不对。未回零、busy、被 disable、限位异常都可能阻止动作。

## 9. 建议下一个人接手后优先补的东西

如果有后续维护计划，建议按这个顺序补强：

1. 协议单元测试
2. 模式切换和回零状态机回归测试
3. 统一日志与故障码
4. 文档里增加主机侧样例帧和调试脚本
5. 视需求再接入 `bucket_volume` 和辅助执行器

## 10. 一句话总结

先抓住 `uart_task -> control_task -> motor_task -> telemetry_service` 这条主线，再看外围兼容链路。只要这条主线理解透了，后续加字段、改模式、调执行策略都会快很多。
