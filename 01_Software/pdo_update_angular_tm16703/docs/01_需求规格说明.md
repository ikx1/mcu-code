# 01 需求规格说明

## 1. 目的

本文档定义 `motor_V2.0.3` 当前版本的实际软件需求，作为联调、测试、维护和后续扩展的基准。本文以当前代码为准，不以历史口头约定或旧协议样例为准。

## 2. 适用范围

系统运行于 `STM32F429 + FreeRTOS` 平台，控制对象为：

- 右驱动轮电机
- 左驱动轮电机
- 升降关节电机
- UART1 主机通信链路
- USART2/USART3/UART4 旧链路兼容服务

## 3. 总体目标

系统需要同时满足以下目标：

- 通过 UART1 接收上位机控制命令并执行。
- 在本地遥控和上位机从机控制之间完成模式切换。
- 对底盘双驱和升降关节进行统一仲裁与执行。
- 在链路异常、急停、回零未完成等条件下进入安全行为。
- 以稳定、可审计的方式上报真实状态。

## 4. 功能需求

### 4.1 启动与任务创建

系统上电后必须完成：

- HAL、时钟、GPIO、DMA、CAN、USART 等基础外设初始化。
- `UserAppTask_Init()` 初始化 CAN 队列、驱动注册、UART1 协议服务、旧串口兼容服务。
- 创建应用任务，包括控制、执行、速度反馈、CAN 维护、急停、WS2812、IBUS、Modbus 等任务。

### 4.2 模式管理

系统主模式包括：

- `MODE_READY`
- `MODE_EMERGENCY`
- `MODE_REMOTE`
- `MODE_DISPLAY`

系统子模式包括：

- `SUB_STOP`
- `SUB_MANUAL`
- `SUB_SLAVE`
- `SUB_CHARGE`
- `SUB_MOTOR_CTRL`
- `SUB_MOTOR_ERR_CLR`
  用于清除滑台报警并重新使能滑台电机。

模式切换规则：

- 急停触发时必须进入 `MODE_EMERGENCY`。
- 遥控链路有效时主模式进入 `MODE_REMOTE`。
- 遥控链路无效时主模式回到 `MODE_READY`。
- 只有 `MODE_REMOTE + SUB_SLAVE` 允许上位机底盘运动命令生效。
- 只有 `MODE_REMOTE + SUB_MOTOR_CTRL` 允许手动关节控制生效。
- `MODE_REMOTE + SUB_MOTOR_ERR_CLR` 允许滑台报警复位并重新使能。
- `MODE_READY` 默认应为无力矩安全待机，不保持驱动轮上电。

### 4.3 UART1 通信协议

UART1 使用固定帧头 + TLV 载荷 + CRC16(Modbus) 的协议。

协议要求：

- 帧头固定为 `A0 0A`。
- 协议版本固定为 `0x01`。
- 当前仅支持 `Telemetry(0x01)` 和 `Command(0x81)`。
- 不发送 `ACK(0x02)`。
- 下发字段采用 Little Endian。
- 未知 Tag 必须跳过，不允许导致解析器失步。
- 已识别字段长度错误或数据越界时，该字段所属域必须拒绝执行。

### 4.4 下发命令需求

当前支持的下发 TLV：

- `0x01`：左轮角速度，`int32`，单位 `mrad/s`
- `0x02`：右轮角速度，`int32`，单位 `mrad/s`
- `0x03`：升降目标高度，`int32`，单位 `mm`
- `0x11`：`status_mask`，`uint16`
- `0x12`：`status_value`，`uint16`

下发行为要求：

- `0x01` 与 `0x02` 必须同帧同时出现，才构成一条完整 drive 命令。
- 单独出现 `0x01` 或 `0x02` 时，drive 域必须丢弃。
- `0x03` 独立生效，不应被 drive 域错误连坐。
- `0x11` 与 `0x12` 必须同帧同时出现，才构成一条 power-policy 命令。
- `status` 域错误时，只能丢弃 power-policy 域，不能连坐 drive/lift 域。
- 对已识别的数值字段，越界时必须拒绝，不允许钳位执行。

### 4.5 控制与执行需求

控制链要求：

- 通信层只维护 host mailbox，不直接操作电机。
- 控制层只生成 `robot_motion_cmd`，不直接下发电机使能/复位。
- 执行层是唯一的电机使能、失能、复位、速度/位置下发入口。

底盘执行要求：

- 上位机 drive 命令只在 `MODE_REMOTE + SUB_SLAVE` 下参与控制。
- 急停时底盘输出必须清零。
- host power-policy 生效时，指定轮被 disable 后必须拒绝上电且速度归零。

关节执行要求：

- 关节必须先完成回零，才允许绝对位置控制。
- 回零流程由执行层状态机独占，不允许控制层直接干预回零动作。
- 上位机升降命令只在新鲜度满足、且回零完成后才允许下发。

### 4.6 遥测需求

上行遥测必须反映真实设备状态，不允许回显 host 意图冒充真值。

当前上行 TLV：

- `0x01`：左轮角速度，`int32`，单位 `mrad/s`
- `0x02`：右轮角速度，`int32`，单位 `mrad/s`
- `0x03`：升降位置，`int32`，单位 `mm`
- `0x13`：`status_word`
- `0x14`：`health_word`
- `0x15`：`alarm_info`
- `0x21`：电池电量，`uint16`，单位 `0.01%`

补充要求：

- `status_word` 只允许来自真实执行状态和真实充电状态。
- `health_word` 只允许来自真实硬件/链路状态。
- `bucket_volume(0x04)` 当前无真实传感器源时，不允许上传伪零值。

### 4.7 安全与保护需求

系统必须具备以下保护：

- 会话超时保护：`1s`
- drive 命令新鲜度保护：`1s`
- lift 命令新鲜度保护：`1s`
- 急停保护：任意时刻优先级最高
- 关节回零超时保护
- CAN 诊断与自动清零维护

超时后的行为要求：

- 会话超时后必须清空 host mailbox 的数据面，并清除锁存状态字。
- drive 命令过期后底盘速度必须回零。
- lift 命令过期后关节命令必须清空。

## 5. 性能需求

### 5.1 周期与频率

当前目标周期：

- UART1 发送周期：`10ms`
- UART1 接收轮询周期：`10ms`
- 控制任务执行周期：`10ms`
- 电机执行任务周期：`10ms`
- 速度反馈任务周期：`10ms`
- 模式输入采样周期：`50ms`

### 5.2 实时性要求

系统应达到：

- UART1 端到端控制链有效更新频率 `100Hz`
- UART1 端到端反馈链有效更新频率 `100Hz`
- 急停和链路失效优先于普通控制命令

## 6. 兼容性需求

系统需要继续保留旧串口兼容能力：

- USART2：显示链路
- USART3：电池/Modbus 链路
- UART4：IBUS 链路

这些兼容链路与 UART1 新协议链路必须解耦，不能相互污染状态所有权。

## 7. 非功能需求

### 7.1 可维护性

必须满足：

- 模块职责单一
- 状态所有权明确
- 控制与执行分层
- 中断与任务边界清晰
- 协议语义可文档化

### 7.2 长期稳定运行

必须满足：

- 不在 ISR 中使用错误的 FreeRTOS 非 ISR API
- 不依赖隐式默认值维持协议契约
- 不允许通信层与执行层双重拥有同一状态
- 错误输入要拒绝，不要转换成高风险动作

## 8. 当前未实现项

以下内容在协议中保留，但当前项目中未接入真实执行器或传感器：

- 喷淋控制真执行器
- 排水控制真执行器
- 夹爪控制真执行器
- `bucket_volume` 真传感器

这些能力在当前版本中不能作为“已实现功能”对外承诺。
