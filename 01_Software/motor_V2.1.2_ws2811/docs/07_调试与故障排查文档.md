# 07 调试与故障排查文档

> 文档状态：当前权威文档
> 适用基线：STM32F429ZET6 + HAL/LL + FreeRTOS(CMSIS-RTOS v2)
> 对应工程：motor_V2.1.1_ws2811
> 说明：本文档按故障现象组织排查路径，适用于现场调试和联调问题定位

## 1. 使用原则

现场排障时，不要一上来就改代码。先回答三个问题：

1. 问题发生在输入、控制、执行还是反馈链路
2. 当前真实状态对象是谁在写
3. 当前看到的是“命令没到”“命令没通过裁决”还是“执行了但反馈不对”

## 2. 建议优先观察的状态点

| 状态点 | 来源 | 用途 |
| --- | --- | --- |
| `host_control_cmd_t` | `uart_task.c` | 判断主机命令是否已正确落地 |
| `ROBOT_MODE_T` | `control_task.c` | 判断当前处于哪种控制模式 |
| `robot_motion_cmd_t` | `control_task.c` | 判断控制层是否生成了执行意图 |
| `input_status_t` | `ScramTask` | 判断急停和限位是否阻断 |
| `motor_info_t` | `bsp_motor_handler.c` | 判断电机当前状态和报警 |
| `motor_joint_home_status_t` | `motor_task.c` | 判断关节回零是否完成或故障 |
| `telemetry_service_snapshot_t` | `telemetry_service.c` | 判断对外上报状态是否正确 |
| `uart_diag_t` | `bsp_uart_driver.c` | 判断 UART FIFO/DMA 是否异常 |
| CAN 诊断计数 | `can_irq_adapter.c` | 判断 bus-off/drop/recover 情况 |

## 4. 按现象排查

### 4.1 现象：UART1 完全不通

排查顺序：

1. 确认 `uart1_init()` 是否执行
2. 确认 `uart_device_init(DEV_UART1)` 是否成功
3. 确认 `USART1_IRQHandler()`、`DMA2_Stream2_IRQHandler()` 是否进入；如怀疑发送链路异常，再检查 `DMA2_Stream7_IRQHandler()`
4. 确认 `uart_read()` 是否读到数据
5. 确认 `uart_parser_feed()` 是否找到帧头并通过 CRC

重点观察：

- `uart_diag_t.rx_isr_bytes`
- `uart_diag_t.rx_drop_bytes`
- `uart_diag_t.rx_bad_isr_state_cnt`

### 4.2 现象：收到命令但不进控制链路

排查顺序：

1. `uart_task_apply_command()` 是否进入
2. `host_control_cmd_t` 是否更新
3. `uart_session_is_alive()` 是否为真
4. `uart_drive_cmd_is_fresh()` 或 `uart_lift_cmd_is_fresh()` 是否为真
5. `ROBOT_MODE_T` 是否已进入 `MODE_REMOTE + SUB_SLAVE`

典型原因：

- 命令 CRC 错误
- 左右轮命令未成对出现
- `status_mask` 和 `status_value` 未成对出现
- 主机 session 已过期

### 4.3 现象：收到命令，模式正确，但车不动

排查顺序：

1. `control_task_apply_slave_motion()` 是否生成了非零 `robot_motion_cmd_t`
2. `Motor_Task()` 内 `host_force_disable()` 是否生效
3. `input_status_t.emergency_flag` 是否置位
4. `motor_task_drive_allow_enable()` 是否允许驱动上电
5. `motor_cmd_set_speed()` 是否被调用

典型原因：

- 刚进入 `SUB_SLAVE`，但还没有新命令通过 seq epoch 检查
- 主机 force disable 有效
- 急停置位
- 驱动未完成 ready 序列

### 4.4 现象：关节不动作

排查顺序：

1. `uart_lift_cmd_is_fresh()` 是否为真
2. `control_task_apply_slave_motion()` 是否生成关节命令
3. `motor_task_joint_is_homed()` 是否为真
4. `motor_task_joint_home_is_busy()` 是否为假
5. `motor_task_apply_joint_motion()` 是否进入实际下发

典型原因：

- 未回零
- 正在回零
- force disable 生效
- 当前模式不允许关节动作
- 驱动状态还未进入 enabled

### 4.5 现象：关节回零失败

排查顺序：

1. 观察 `motor_joint_home_status_t.state`
2. 确认 `input_status_t.limit_lower` 是否按预期变化
3. 确认回零期间是否出现 `JOINT_ALARM`
4. 检查 `SYSTEM_CFG_JOINT_HOME_TIMEOUT_MS` 是否过短
5. 检查 `SYSTEM_CFG_JOINT_HOME_NEG_TARGET_POS_CMD` 是否合理

典型原因：

- 下限位极性错误
- 机构未触发限位
- 回零速度和超时配置不匹配
- 关节驱动报警导致进入 fault

### 4.6 现象：遥测不对或值不更新

排查顺序：

1. `Robot_Speed_Task()` 是否更新 `drive_feedback_t`
2. `BatteryHandler_Snapshot()` 是否返回有效数据
3. `ibus_handler_snapshot()` 是否有效
4. `telemetry_service_snapshot()` 是否取到最新值
5. `uart_task_build_telemetry_frame()` 是否按 100Hz 发送

典型原因：

- 实际反馈未更新
- 误把命令值当成反馈值在看
- 电池/IBUS 链路未更新
- 遥测周期被误改

### 4.7 现象：CAN 丢帧或恢复异常

排查顺序：

1. `mcu_can1_sce_irq_adapter()` 是否记录错误
2. `mcu_can_diag_poll_recover()` 是否在恢复
3. `can_rx_fifo_drop_count_get()` 是否持续增加
4. `can_queue_pending_count_get()` 是否堆积
5. `can_poll_parse_loop()` 是否在持续消费 RX FIFO

重点观察：

- `busoff_count`
- `recover_pending`
- `recover_ok_count`
- `recover_fail_count`
- `can_rx_fifo_drop_count`

## 5. 调试顺序建议

### 5.1 主机联调

推荐顺序：

1. 确认 UART1 有帧
2. 确认命令入 mailbox
3. 确认模式进入 `SUB_SLAVE`
4. 确认生成 `robot_motion_cmd_t`
5. 确认执行层未拦截
6. 确认遥测正确回传

### 5.2 实车动作异常

推荐顺序：

1. 先看急停和限位
2. 再看当前模式
3. 再看驱动状态和报警
4. 最后看控制换算和主机命令本身

## 6. 调试时的常见误区

- 误把 `robot_motion_cmd_t` 当作真实反馈
- 误把 `status_word` 当作主机意图回显
- 看到命令收到了，就以为执行层一定会动作
- 忽略 `SUB_SLAVE` 切入后的新命令要求
- 改控制层逻辑，却不检查执行层安全门是否仍然拦截

## 7. 现场快速结论模板

遇到问题后，建议按下面格式归纳：

- 问题阶段：输入 / 控制 / 执行 / 反馈
- 当前模式：`MODE_xxx + SUB_xxx`
- 主机链路：session 是否 alive，命令是否 fresh
- 执行约束：急停、回零、disable、报警是否存在
- 反馈链路：CAN 是否正常，遥测是否反映真实状态

只要按这个模板梳理，绝大多数问题都能快速缩小范围。
