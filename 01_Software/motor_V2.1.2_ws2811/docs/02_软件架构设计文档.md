# 02 软件架构设计文档

> 文档状态：当前权威文档
> 适用基线：STM32F429ZET6 + HAL/LL + FreeRTOS(CMSIS-RTOS v2)
> 对应工程：motor_V2.1.1_ws2811
> 说明：本文档描述当前源码实现下的分层架构、任务关系、主数据流和关键状态对象

## 1. 架构目标

当前工程的软件架构有四个核心目标：

1. 将主机通信、遥控输入、执行控制、电机反馈和状态呈现解耦
2. 让主机控制和遥控控制共用统一执行路径
3. 把安全裁决集中在执行层，避免通信层直接驱动动作
4. 让对外遥测基于真实状态，而不是控制意图

## 2. 总体分层

### 2.1 分层结构

```text
应用展示层
    显示 / 灯带 / 遥测回传

业务控制层
    控制任务 / 模式机 / 运动意图生成

业务执行层
    电机执行 / 回零 / 上电策略 / 故障恢复

业务通信层
    UART1 新协议 / IBUS / Battery / Display

驱动集成层
    uart_stack / uart_rtos / bsp_* handler

MCU 抽象层
    uart_port / can_port / gpio_port / irq_adapter

板级外设层
    GPIO / UART / CAN / TIM / DMA / IRQ
```

### 2.2 每层职责

| 层级 | 主要目录 | 职责 |
| --- | --- | --- |
| 展示层 | `User/ws2812_task`, `display_handler`, `uart_task` | 呈现状态给人或上位机 |
| 控制层 | `User/control_task` | 模式选择、运动意图生成 |
| 执行层 | `User/motor_task` | 电机状态机、安全裁决、运动执行 |
| 通信层 | `User/communication_task`, `User/ibus_task`, `User/battery_task` | 接收主机、遥控、电池等外部输入 |
| 驱动集成层 | `BSP_Plantform/*`, `Middlewares/components/*` | 协议、队列、业务驱动封装 |
| MCU 抽象层 | `MCU_Platform/*` | 芯片相关适配 |
| 板级层 | `Core/Src/*` | 外设初始化、中断入口 |

## 3. 启动架构

### 3.1 启动路径

系统启动路径如下：

```text
main()
-> HAL_Init / SystemClock_Config / MX_* 外设初始化
-> osKernelInitialize()
-> MX_FREERTOS_Init()
-> 在 `freertos.c` 中创建 `defaultTask`
-> `MX_FREERTOS_Init()` 内调用 `UserAppTask_Init()`
-> osKernelStart()
```

### 3.2 启动顺序设计原因

当前启动顺序是刻意设计的：

- 先初始化 `CAN queue` 和电机对象，保证后续执行层能拿到驱动状态
- 再启动 UART1 新协议服务，保证主机收发在调度器运行后立即可用
- 最后创建应用任务，保证上层任务不会先于底层服务运行

## 4. 任务架构

### 4.1 当前任务列表

| 任务 | 周期 | 作用 | 架构层级 |
| --- | --- | --- | --- |
| `ScramTask` | 10ms | 更新急停、限位输入 | 通信/输入层 |
| `ContronlTask` | 10ms 主循环，50ms 模式更新 | 模式机和运动意图生成 | 控制层 |
| `Motor_Task` | 10ms | 执行裁决与动作下发 | 执行层 |
| `Can_Analy_Task` | 1 tick 轮询 | CAN 恢复、报文解析、UART 诊断维护 | 驱动集成层 |
| `Robot_Speed_Task` | 10ms | 从电机反馈生成真实轮速 | 执行/反馈层 |
| `user_legacy_rx_service_task` | 1ms | 轮询旧串口桥接收包 | 通信层 |
| `ibusTask` | 10ms | IBUS 超时维护 | 通信层 |
| `ModbusTask` | 2000ms | 电池查询与链路检查 | 通信层 |
| `WS2812_Task` | 50ms | RGB 灯带展示 | 展示层 |
| `UART_TX` | 配置周期 | UART1 发包 | 通信层 |
| `UART_RX` | 配置周期 | UART1 收包 | 通信层 |
| `UART_DMA_SVC` | 1ms 唤醒 | UART1 DMA 共享服务 | 驱动集成层 |

### 4.2 任务关系

```text
ScramTask -> input_status
legacy_rx / ibusTask / ModbusTask -> 外部输入状态
UART_RX -> host_control_cmd
ContronlTask -> robot_motion_cmd / robot_mode
Motor_Task -> 电机上电、复位、运动、关节控制
Can_Analy_Task -> motor_info / motor_runtime
Robot_Speed_Task -> drive_feedback
telemetry_service -> snapshot
UART_TX -> telemetry 上报
WS2812_Task / display_handler -> 现场状态呈现
```

## 5. 核心数据流

### 5.1 主机命令数据流

```text
USART1 + DMA
-> uart_irq_adapter
-> bsp_uart_driver
-> uart_rtos
-> uart_stack
-> host_protocol parser
-> uart_task_apply_command
-> host_control_cmd_t
-> control_task
-> robot_motion_cmd_t
-> motor_task
-> CAN 驱动
```

这条链路体现了当前架构最重要的一条原则：

> 主机命令必须先落地为统一状态对象，再被控制层和执行层消费，不能绕过中间层直接操作电机。

### 5.2 遥控输入数据流

```text
UART4
-> legacy bridge
-> ibus_callback
-> IBUS_Handler
-> control_task robot_mode_update_50ms
-> SUB_MANUAL / SUB_MOTOR_CTRL 等子模式
-> robot_motion_cmd_t
-> motor_task
```

### 5.3 电机反馈数据流

```text
CAN IRQ
-> can_irq_adapter
-> can_queue RX FIFO
-> can_poll_parse_loop
-> bsp_motor_handler
-> motor_info_t / motor_runtime_t
-> Robot_Speed_Task
-> drive_feedback_t
-> telemetry_service
```

### 5.4 状态回传数据流

```text
drive_feedback + battery + IBUS + input + motor_info
-> telemetry_service_snapshot
-> uart_task_build_telemetry_frame
-> UART1 遥测输出
```

## 6. 关键状态对象与所有权

### 6.1 为什么要强调状态对象所有权

本工程不是通过大量函数参数链式传递状态，而是通过少数共享状态对象协作。为了避免竞争和逻辑混乱，当前架构有明确的“谁写谁读”边界。

### 6.2 状态对象表

| 状态对象 | 写入者 | 读取者 | 含义 |
| --- | --- | --- | --- |
| `host_control_cmd_t` | `uart_task.c` | `control_task.c`, `motor_task.c` | 主机命令 mailbox |
| `robot_motion_cmd_t` | `control_task.c` | `motor_task.c` | 控制层生成的统一执行意图 |
| `ROBOT_MODE_T` | `control_task.c` | 执行层、显示层、灯带层 | 当前主模式与子模式 |
| `input_status_t` | `ScramTask` | 控制层、执行层、遥测层 | 急停和限位 |
| `IBUS_Handler` | `ibus_callback` 和超时逻辑 | 控制层、遥测层 | 遥控状态 |
| `motor_info_t` | `bsp_motor_handler.c` | 执行层、反馈层、遥测层 | 电机实际反馈信息 |
| `drive_feedback_t` | `Robot_Speed_Task` | 遥测层 | 真实轮速反馈 |
| `telemetry_service_snapshot_t` | `telemetry_service.c` | `uart_task.c` | 对外上报的状态快照 |

### 6.3 当前共享状态的设计原则

- 通信层拥有主机命令 mailbox 的唯一写入口
- 控制层拥有运动意图的唯一写入口
- 执行层拥有电机最终动作的唯一写入口
- 遥测层拥有对外真实状态聚合的唯一写入口

这让每个问题都可以沿着“这个状态是谁写的”快速回溯。

## 7. 控制架构

### 7.1 主模式和子模式

控制层把系统运行状态分为主模式和子模式：

- 主模式：`MODE_READY`, `MODE_EMERGENCY`, `MODE_REMOTE`
- 子模式：`SUB_STOP`, `SUB_MANUAL`, `SUB_SLAVE`, `SUB_CHARGE`, `SUB_MOTOR_CTRL`, `SUB_MOTOR_ERR_CLR`

### 7.2 控制层职责边界

控制层只做三类事情：

1. 根据输入状态决定当前模式
2. 根据模式决定当前控制来源
3. 把控制来源翻译成统一的 `robot_motion_cmd_t`

控制层不负责：

- 直接判断驱动是否允许上电
- 直接下发 CAN 帧
- 直接决定遥测值

### 7.3 为什么控制层不能直接执行

如果控制层直接执行动作，会产生两个严重问题：

- 主机命令和遥控命令的执行路径不统一
- 急停、失联、force disable、未回零等安全裁决会被分散到多个地方

因此当前架构把最终裁决集中放在 `Motor_Task`。

## 8. 执行架构

### 8.1 执行层职责

执行层负责：

- reset 边沿处理
- 电机初始化和 ready 序列
- 驱动轮 enable/disable 判定
- 左右轮速度执行
- 关节 power hold 判定
- 关节回零状态机
- 关节运动执行
- 关节故障清除逻辑

### 8.2 安全裁决位置

以下约束在执行层统一生效：

- 急停
- 主机 force disable
- 模式是否允许控制
- 会话是否仍然有效
- 回零是否完成
- 关节是否 busy

因此，从架构设计上说：

> 控制层可以提出“想动”，但执行层保留“允许不允许动”的最终权力。

## 9. 通信架构

### 9.1 UART1 新协议栈

UART1 新协议栈由以下层级组成：

```text
IRQ/DMA
-> uart_port
-> bsp_uart_driver
-> uart_rtos
-> uart_stack
-> host_protocol
-> uart_task
```

各层分工如下：

- `uart_port`：只做 MCU DMA 适配
- `bsp_uart_driver`：维护 TX/RX FIFO 和诊断计数
- `uart_rtos`：创建 TX/RX 任务和共享 DMA 服务任务
- `uart_stack`：把字节流提升为协议帧
- `host_protocol`：CRC、帧解析、TLV 编解码
- `uart_task`：命令落地和遥测封装

### 9.2 传统串口链路

当前系统保留三条旧式串口桥接：

- IBUS
- Battery Modbus
- Display
- Ultrasonic 预留

因此通信架构不是“全部统一协议栈”，而是“UART1 新栈 + 旧桥接并存”。

## 10. 反馈与遥测架构

### 10.1 反馈来源

当前对外状态不是直接从命令值生成，而是来自：

- 电机反馈
- GPIO 输入
- 电池状态
- IBUS 状态
- CAN 诊断维护结果

### 10.2 遥测聚合点

`telemetry_service_snapshot()` 是整个系统唯一的真实状态聚合点。

其设计意义在于：

- 避免多个模块各自拼一部分遥测
- 避免主机意图和真实状态混淆
- 让调试时有一个统一入口看“系统最终对外说了什么”

## 11. 板级与驱动适配架构

### 11.1 板级层与 MCU 抽象层的关系

`Core/Src` 负责真正的外设初始化和中断入口，`MCU_Platform` 负责对这些硬件能力做轻量适配。

这种分法的好处是：

- 板级引脚和寄存器配置集中
- 上层驱动不直接依赖具体 IRQ 寄存器
- 迁移板级时更容易定位需要调整的范围

### 11.2 当前可迁移和不可迁移的部分

相对容易迁移：

- GPIO 映射
- UART 引脚映射
- TIM/DMA 灯带映射
- CAN GPIO 和过滤器初始化

不建议轻易打散：

- `uart_task -> control_task -> motor_task` 的控制主线
- 关节回零状态机与执行层裁决
- `telemetry_service` 的真实状态聚合设计

## 12. 当前架构的优点与代价

### 12.1 优点

- 控制和执行分层清晰
- 主机和遥控共用统一执行链路
- 遥测与命令意图分离
- CAN、UART、GPIO 适配边界较清楚
- 适合在不重构整套工程的前提下继续演进

### 12.2 代价

- 新旧串口链路并存，理解成本较高
- 历史命名较多，阅读时需要结合实际行为
- 关节回零逻辑集中且复杂，修改风险高
- 当前缺少系统化自动化测试，文档和断点阅读仍是主要接手手段
